## 2. 本次修复的"真实缺陷"

### 2.1 两个暂停/继续用例从未运行过

- 现象：`SyncManagerTests` 的两个新用例（`pauseThenResumeCompletesTheRun`、`pausedRunKeepsCheckpointsForRecovery`）在 v2 首次全量构建后失败。
- 定位：v1 的测试可执行文件生成时间（17:44:58）早于测试源码最后修改时间（17:46:17），即这两个用例在 v1 从未被编译运行过；v1 的"174 通过"对应的是更早的一轮。
- 根因（测试缺陷，不是产品缺陷）：用例假设"第一门课完成后任务仍在运行"，但测试夹具把课程间隔设为 0，而回放桥是同步回调 —— 整轮同步在 `start()` 返回前就跑完，`pause()` 落在终态之后，变成空操作。
- 修复：给这两个用例设置 `pauseBetweenCoursesMs = 30`，制造与真实运行一致的异步窗口；`pause()` 在窗口期内生效，`resume()` 后继续完成整轮。

### 2.2 GUI 离屏测试挂起（本机实测的新问题）

- 现象：`MainWindowSmokeTests`（以及同为 WebEngine 程序的 `njulms_verify.exe`、v1 的历史构建）在某次运行后开始 180s 超时；进程 CPU 接近 0，无子进程。
- 定位（最小探针，逐步标记）：
  1. 从 Qt 安装目录（`D:\Qt\...\bin` + `plugins`）运行时，探针 2 秒内走完 `QApplication → QWebEngineProfile → QWebEnginePage → QWebEngineView → 加载 about:blank`，完全正常；
  2. 把同一探针放进部署目录 `build\bin` 后，进程停在 `QApplication` 构造；
  3. 用 `QT_QPA_PLATFORM=windows`（部署目录里有 `qwindowsd.dll`）或显式设置 `QT_PLUGIN_PATH` 指到 Qt 插件目录，都能正常启动；
  4. 把 `qoffscreend.dll` 复制进 `build\bin\platforms\` 后，`QT_QPA_PLATFORM=offscreen` 立即恢复正常。
- 结论：部署目录存在 `platforms/` 但缺少 offscreen 插件时，Qt 的平台插件查找会卡住（同一台机器上 v1/v2 两套部署目录都能复现；直接使用 Qt 安装目录不受影响）。
- 修复：`tests/CMakeLists.txt` 增加 POST_BUILD 步骤，把 `Qt6::QOffscreenIntegrationPlugin` 部署到测试可执行文件旁的 `platforms/`。测试因此不再依赖插件搜索路径的回退行为。
- 影响范围：只影响"用 offscreen 平台跑 GUI 测试"的场景；用户正常双击运行的程序使用 `windows` 平台，不受影响。

### 2.3 控制台被站点自身的 console.log 刷屏

## 5. 采集性能与正确性改造（2026-10-09 晚，本轮）

### 5.1 正确性：快照完整性参与写入判定

原实现里 `snapshotComplete` 只用于统计，快照不完整时仍会做缺失检测并推进断点。现修正为：

| 位置 | 行为 |
| --- | --- |
| 缺失检测 | **仅当 `snapshotComplete == true`** 才把"本轮没出现的旧记录"标记 `present = 0`；不完整时跳过（避免把没取到的作业误判成"消失"） |
| 课程断点 | 该课程的 `sync_state.full_scan_completed` 跟随 `snapshotComplete`，不完整时保持 0 |
| 整轮终态 | 只要有一门课程快照不完整，整轮即为 `partial`（不再报 `success`）；消息里写明"X 门快照不完整" |
| 数据本身 | 取到的数据照旧写入（`保证不漏`），只是不做否定性结论 |

对应测试：`RepositoryTests::snapshot_incompleteSnapshotKeepsRowsAndBreakpoint`、
`SyncManagerTests::incompleteSnapshotDoesNotSoftDeleteExistingAssignments`。

### 5.2 写放大：未变记录不再逐行更新

原先每条"内容未变"的作业都会执行一次 `UPDATE ... SET last_seen_at`，同步一轮的写入量是
O(作业总数)。现在：

- 内容未变**且**该记录本来就在场（`present = 1`）→ **完全不写**，只计入 `unchanged`；
- 内容未变但此前被软删除过 → 仍然写一次把 `present` 恢复为 1（保证"复活"正确）；
- 每门课在事务末尾执行 1 条 `UPDATE courses SET last_synced_at, assignment_count`，
  用课程级时间戳替代逐行的 `last_seen_at`。

结果：单轮写入量从 O(作业总数) 降到 **O(变化条数) + O(课程数)**。
对应测试：`RepositoryTests::snapshot_unchangedRowsAreNotRewritten`、
`RepositoryTests::snapshot_reappearingAssignmentIsRestored`。

### 5.3 历史表保留策略

`crawl_runs` / `crawl_batches` / `parse_errors` 原先只增不减（按小时级同步跑一年约 20 万行）。
新增 `SqliteRepository::pruneCrawlHistory(keepRuns = 200, keepDays = 30)`，每轮同步结束后自动执行，
同时满足"保留最近 200 轮"与"保留最近 30 天"两个下限。
对应测试：`RepositoryTests::runs_pruneKeepsRecentHistoryOnly`。

### 5.4 SQLite 调优与结构版本 2

- 新增 `PRAGMA journal_size_limit = 8MB`、`PRAGMA wal_autocheckpoint = 1000`；
- 结构版本 `1 → 2`：`courses` 增加 `last_synced_at`、`assignment_count`，
  迁移用 `ALTER TABLE ... ADD COLUMN`（先查 `PRAGMA table_info`，可幂等重放），
  旧库打开时自动升级，无需手动重建。
  对应测试：`RepositoryTests::schema_migratesV1DatabaseToV2`（手工造 v1 库 → 打开 → 校验列与版本）。

### 5.5 接口探索：发现跨课程聚合接口 `/api/todos`

为了评估"能不能少发请求"，给验证工具加了只读探测：从页面已加载的 120 个 `/static/*.js`
bundle 中静态提取 `/api/...` 路径（扫了前 60 个、约 8 MB，得到 264 条），再对候选路径做只读 GET。

结果：

```
/api/todos -> status=200 bytes=366 keys=todo_list
  items=1，item keys: course_code,course_id,course_name,course_type,end_time,id,is_locked,
                      is_student,prerequisites,title,type
  distinct types: homework
/api/todo-list、/api/todo_list、/api/upcoming、/api/calendar/activities -> 404
/api/activities?type=homework -> 500（站点自身故障）
```

**结论**：存在一个真实的"待办聚合"接口 `/api/todos`（跨课程、含 `course_id` 与 `end_time`），
但它只覆盖"待办/未完成"这类条目，**不能**替代完整快照（历史、已提交、被封存的活动都不在其中）。
因此它的定位是"变更信号 + 按需深扫"，并保留低频的全量对账 —— 第 6 节记录了该改造。

## 6. 快速增量：待办变更信号 + 按需深扫（2026-10-09 晚，本轮）

### 6.1 目标与取舍

| 项 | 说明 |
| --- | --- |
| 常态成本 | 从 **N+1 个请求**（1 课程列表 + 每门课一个作业请求）降到 **2 个请求**（`my-courses` + `todos`） |
| 立即反映的变化 | 待办出现/消失、截止时间变化、库里还没有的新条目 |
| 延迟反映的变化 | 待办接口看不到的（标题/说明被改、已提交项、历史项）→ 由**周期性全量对账**兜住（默认 24 小时） |
| 安全底线 | 接口不可用/形态变化、或尚无全量基线时，**自动回退到完整扫描**；绝不把"接口坏了"当成"没有变化" |

## 7. 启动自动全量扫描（2026-10-09 晚，本轮）

### 7.1 需求与做法

需求：**每次启动都完整扫描一遍**，同时注意性能。

实现（`MainWindow`）：

1. 启动后仍按既有流程自动打开站点；
2. 页面第一次成功加载到 `lms.nju.edu.cn` 时执行"启动动作"（只执行一次）：
   - 默认 → 走一次**完整全量扫描**（`SyncManager::Mode::Full`）；
   - 若开关关闭 → 只做一次会话检查；
3. 开关「启动时自动全量扫描（保证数据最新）」默认开启，偏好写入 `QSettings`
   （`sync/startupFullScan`），下次启动沿用；
4. 停在统一身份认证页面时不触发；登录完成回跳本站后会自动补上这次扫描。

### 7.2 性能优化（关键点）

| 优化 | 说明 |
| --- | --- |
| **合并请求** | 全量扫描自身的第一步就是会话检查，因此启动时不再额外调用一次 `AuthManager::check` —— 比"先检查登录再扫描"**少一个请求** |
| **不重复导航** | 复用启动时已经加载好的页面与同一份会话，不额外打开页面 |
| **最短间隔保护** | 距上次**成功全量扫描**不足 5 分钟时跳过启动扫描，只做登录检查——避免"刚扫完就重启"造成重复的一整轮请求 |
| **与调度去重** | 启动扫描是一次正常的 Full 运行，会写入"全量对账标记"，因此定时任务不会紧接着再跑一次全量 |
| **并发保护** | 启动扫描走统一的 `beginSync()` 入口：已有任务在跑时直接忽略；页面未就绪时先自动打开站点 |
| **不阻塞界面** | 全程异步（沿用既有信号槽与批次事务），界面可正常操作，也可以随时暂停/取消 |
| **保留限速** | 请求节奏维持 400 ms/请求 + 300 ms/课程（合规优先），13 门课约 9 秒 |

### 7.3 真机验证（隔离环境：临时数据/日志目录 + 真实 Profile）

第一次启动（无全量基线）：

```
20:29:07  single-instance lock acquired
20:29:08  navigating to "https://lms.nju.edu.cn/user/index"
20:29:15  startup: running a full scan as configured
20:29:15  sync started; mode: full run: 1
20:29:17  discovered 13 course(s)
20:29:24  sync finished; outcome: 0 courses: 13 / 13 inserted: 7 updated: 0 durationMs: 9216
```

第二次启动（距上次全量不足 5 分钟）：

```

```

即：**第一次启动自动全量成功（13/13 课程，9.2 秒）**；**紧接着再启动时被 5 分钟保护拦下**，
只做了一次登录检查（1 个请求）——正是"每次启动都全量 + 注意性能"的预期行为。

## 9. 数据清空按钮 + 浏览器窗口隐藏（2026-10-09 晚，本轮）

### 9.1 「删除全部数据（保留登录状态）」按钮

- 位置：「数据」页底部 → **危险操作** 区。
- 行为：二次确认（默认选「否」）后，清空本地数据库中的
  `assignments` / `courses` / `sync_state` / `crawl_runs` / `crawl_batches` / `parse_errors`，
  保留 `schema_version`（表结构不变，清空后可以继续写入）。
- **不删除**：浏览器 Profile（登录状态保留，不需要重新扫码/过滑块）、日志文件。
- 安全措施：
  - 有同步任务在跑时直接拒绝执行并提示（避免删到一半与写入互相干扰）；
  - 整个清空在一个事务里完成，任何一步失败都整体回滚（要么全删，要么不动）；
  - 结束后尽力执行一次 `VACUUM` 回收磁盘空间（失败不影响"已清空"这个结果）。
- 实现：`SqliteRepository::clearAllData()`；UI 侧删除后立即刷新课程表、作业表、最近一次同步结果。

### 9.2 浏览器页面隐藏 + 按需弹出

原来浏览器视图嵌在「采集」页的下半部分（QSplitter），现在改为**独立顶层窗口**、默认隐藏：

| 时机 | 行为 |
| --- | --- |
| 程序启动（会话有效） | 页面在隐藏窗口中加载，界面看不到浏览器；同步照常 |
| 会话失效 / 需要登录 | **自动弹出**登录窗口（`loginPageReached` 与 `AuthState::NeedLogin` 两处触发） |
| 登录成功 | **自动隐藏**（`AuthState::Authenticated`；同步成功时也会用 `markAuthenticated` 刷新状态） |
| 手动点「打开智汇南雍并登录」 | 显示该窗口（页面不在本站时顺带加载首页） |
| 点窗口的关闭按钮 | 只隐藏、不销毁（页面与会话继续为后台取数服务） |

实现要点：

- 视图不再重挂父窗口（避免 WebEngine 重绘/上下文问题）——它始终属于同一个 `LoginWindow`；
- 隐藏的 QWebEngineView 仍能执行 `runJavaScript` 与 fetch（命令行验证工具一直是这种用法，实测可用），
  因此"后台取数 + 需要时才显示页面"成立；
- 同步成功后通过 `AuthManager::markAuthenticated()` 刷新登录状态，顺带触发窗口自动隐藏，
  状态栏也会显示"已登录（可访问 N 门课程）"。

## 10. 性能实测：Debug vs Release（2026-10-09 晚）

用户反馈"打开的网页好卡"。定位结论：**不是逻辑问题，是构建配置问题** ——
此前所有版本都是 **Debug 构建**（Qt/Chromium 调试版不含优化，使用调试分配器，
而且 Debug 版还额外挂着控制台窗口在写 stderr）。

同一台机器、同一份登录会话、同一个站点页面的实测对比：

| 指标 | Debug | Release |
| --- | --- | --- |
| 页面加载（导航 → `loadFinished`，即"页面能用了"） | **6.8 – 9.6 秒** | **1.13 秒** |
| 全量扫描 13 门课程 | 9.2 – 9.6 秒 | 8.47 秒（受 400 ms/请求限速支配，几乎不变） |
| 进程内存 | 主进程 + WebEngine 合计数百 MB（Debug DLL 723 MB 常驻映像） | 主进程 248 MB + WebEngine 176 MB |
| exe 体积 | 1.5 MB | 0.5 MB |
| 控制台窗口 | 有 | 无（`WIN32_EXECUTABLE` 仅对非 Debug 生效） |

结论与做法：

- **日常使用改用 Release 构建**：`.\build.ps1 -QtPrefix 'D:\Qt\6.8.3\msvc2022_64' -Config Release`
  （数据、日志、Profile 都在可执行文件同级目录，切换构建不会影响登录状态）；
- Debug 构建保留给排查问题使用（`-Config Debug`）；
- 全量扫描的 ~8.5 秒来自刻意限速（400 ms/请求 + 300 ms/课程），与卡顿无关，
  且完全在后台跑、不阻塞界面；
- 切换后 `build\bin` 会同时留着 Debug 与 Release 两套 Qt 运行库（Debug 那套约 723 MB
  已不再被使用，可手动清理）。

## 15. 缺陷修复：全量采集被误当成"快速检查"而跳过所有课程（2026-10-10）

### 15.1 现象（用户报的）

点「开始全量采集」，日志/摘要却是「快速检查完成：13 门课程均无变化」，
一个作业请求都没发出去 —— 全量采集没有真的爬取课程。

### 15.2 根因

`SyncManager` 里负责"跳过无变化课程"的两个状态字段只在快速路径分支里被赋值，
**没有在每轮开始时重置**：

```cpp
// start() 的"重置本轮状态"里缺了这三行
bool quickDiffActive = false;          // 第 62 行
QSet<QString> quickChangedCourses;     // 第 64 行
QStringList quickTodoLines;
```

- 增量 + 快速路径：`quickDiffActive = true`，`quickChangedCourses` = 待办差异算出的集合；
- 接着点全量：`mode = Full`，但这两个字段还留着上一轮的值；
- `processNextCourse()` 只判断 `quickDiffActive && !quickChangedCourses.contains(...)`，
  **没有判断模式** → 全量的每一门课都被当成"无变化"跳过。

### 15.3 修复（三处，含双重保险）

| 位置 | 改动 |
| --- | --- |
| `SyncManager::start()` | 每轮开始显式清空 `quickDiffActive` / `quickChangedCourses` / `quickTodoLines` |
| `SyncManager::processNextCourse()` | 跳过条件加上 `d->mode == Mode::Incremental`，即使标志位被污染，全量也绝不跳过 |
| `SyncManager::finishRun()` | 写"待办基线"同样要求 `mode == Incremental`，避免全量轮次误写增量基线 |

### 15.4 验证

| 检查项 | 结果 |
| --- | --- |
| 回归用例 | 新增 `SyncManagerTests::fullScanAfterQuickIncrementalStillFetchesEveryCourse`：先跑一轮"待办无变化"的增量（断言 2 门课全跳过），再跑全量，断言 `coursesSkipped == 0`、两门课都真的发了作业请求 |
| 修复前 | 该用例失败：`Actual (summary.coursesSkipped): 2 / Expected: 0`（先复现再修） |

## 22. 缺陷修复：PC 没开机时打开网页 app 会一片空白（2026-10-10）

### 22.1 现象（用户报的）

PC 上的程序没打开，直接点开 iPad 的网页 app → **页面一直空白**，
必须从后台任务里划掉、重开才有反应。

### 22.2 根因

网页 app 的所有内容都来自 PC：程序没运行时，`tailscale serve` 的代理没有上游，
页面**根本没被加载过**（拿不到 HTML/JS），自然也没有任何代码可以自我恢复 ——
只能靠用户重开。这与"前端资源不缓存"的既有设计叠加，就成了死局。

### 22.3 修复：离线外壳（Service Worker）

| 位置 | 改动 |
| --- | --- |
| 新增 `resources/web/service-worker.js` | 缓存页面外壳：`/`（HTML）+ 带版本号的 `app.js` / `style.css` / 图标；页面导航**网络优先、失败回落缓存**；`/api/*` 永不缓存 |
| 安装阶段预取资源 | 从 HTML 里解析出 `src/href` 指向的资源一并缓存 —— **页面首次打开时还不受 SW 控制**，只缓存 HTML 会导致离线时 JS 加载失败（第一版实现就踩了这个坑，实测缓存里只有 `/`） |
| `WebServer` | 新增 `/service-worker.js` 路由；它的 `Cache-Control` 用 `no-cache`（浏览器要求 SW 脚本可缓存/复验，`no-store` 会被拒绝），其余资源仍是 `no-store` |
| `app.js` | 注册 SW（HTTPS 或 localhost）；连不上时把两个列表换成明确的说明文案（而不是停在"正在读取…"）；`connectedOnce` 决定红标是**立刻**亮还是等 8 秒；顺手修掉错误提示重复拼接（"无法连接…：无法连接…"） |

| 步骤 | 结果 |
| --- | --- |
| 在线打开一次 | SW 就绪，缓存内容：`/`、`/apple-touch-icon.png`、`/style.css?v=…`、`/app.js?v=…` |
| 关闭后端 + **重新加载页面** | `blank = false`（**不再空白**）、红色"连接中断"立刻显示、两个列表显示"连不上 PC 上的采集器…程序启动后本页会自动刷新，不需要重开" |

### 22.5 补充：走 Tailscale 时 502 也会被当成"正常响应"

第一版离线外壳在本机 `127.0.0.1` 上验证通过，但用户反馈 iPad 上**仍然空白**。
改用**真实 Tailscale 地址**复现后发现差别：

| 路径 | 后端关闭时的表现 | 结果 |
| --- | --- | --- |
| `http://127.0.0.1:8790/` | TCP 连接被拒绝 → `fetch` 抛异常 | 走 catch 分支 → 回落缓存 ✓（所以第一版"通过"了） |
| `https://laptop-….ts.net/` | **tailscale serve 返回 502 空响应** → `fetch` 正常返回 | 代码把 502 当正常响应交给浏览器 → **空白页** ✗ |

修复：Service Worker 在导航/资源请求收到非 2xx（≥500）时，先看缓存里有没有可用副本，
有就返回缓存；前端把"无响应体的 5xx"翻译成"PC 上的程序没有运行"，而不是显示 `HTTP 502`。

复测（真实 Tailscale 地址，完整走一遍）：在线打开 → SW 就绪且接管页面（`hasController=true`）
→ 关闭后端并重载 → **不空白**、红标显示、提示"连不上 PC 上的采集器：PC 上的程序没有运行"
→ 重启后端 → 页面自动恢复（列表回数据、红标消失、状态"空闲"），全程未重开页面。

> 注意：已经装过旧版离线外壳的设备，需要**在线打开一次**让外壳自动更新（SW 脚本每次都会
> 回源校验，`skipWaiting + clients.claim` 会立即接管），之后离线行为就正常了。

## 23. 性能排查：用户报"一开程序整机就卡"（2026-10-10）

### 23.1 实测（同一台机器，24 核，逐秒采样）

| 场景 | 整机 CPU | 本程序 | WebEngine | 磁盘 | GPU |
| --- | --- | --- | --- | --- | --- |
| 空闲（程序在跑） | 8.6% | 0.1% 单核 | 0% | — | — |
| 冷启动 30 秒 | 峰值 19% | 峰值 3.5% 单核 | 3.5% 单核 | — | — |
| 完整全量采集（13 门课） | 峰值 16%，均值 6% | **峰值 5.7% 单核** | 7.6% 单核 | ≤3% | — |
| 登录窗口渲染原站页面 | 峰值 16% | 2.8% 单核 | 2.7% 单核 | — | 无增量 |

内存约 380 MB；GPU 在"程序关闭"与"程序运行"两种情况下都是 **~19% 基线**（差值在噪声内）。

结论：**本程序不是整机卡顿的来源**——它的峰值只有"单核的 6%"，折合整机 0.25%。
同一时刻机器上真正的 GPU/CPU 消耗者是其它常驻软件（IntelGraphicsSoftware 累计 1091 s CPU、
ChatGPT 三个进程 700+ MB、ArmouryCrate、HipsTray 等），GPU 基线 19% 在程序未运行时就已经存在。

### 23.2 仍然做的对症改动：进程优先级

即便不是元凶，"后台采集器跟前台抢 CPU"本身就不合理。`main.cpp` 里启动时把自己降到
**低于正常（BelowNormal）**优先级，QtWebEngine 的子进程继承后 Chromium 还会进一步降到
**Idle**：启动扫描/定时采集这类批量工作让位给用户的编辑器与输入法。

实测（构建后运行）：

```
njulms_app           pid=35500   优先级=BelowNormal
QtWebEngineProcess   pid=17660   优先级=Idle
```

### 23.3 给用户的排查建议

卡顿时打开任务管理器（Ctrl+Shift+Esc）→ 按 CPU 排序，并在"详细信息"里看 GPU 列，
把前三个进程名发来。另外两个常见嫌疑值得单独试：

1. **杀毒/HIPS 实时扫描**（HipsTray / Defender）扫描浏览器 Profile 与 SQLite WAL 时，
   会出现"CPU 不高但打字发涩"的现象；可把程序目录加入排除项验证。
2. **Intel 显卡软件 / ArmouryCrate** 这类常驻工具，GPU 基线 19% 就是它们贡献的。

### 24.4 三个值得记住的坑（详版在 docs/06 第 7 节）

1. **所有页面内容都由 JS 再渲染一步**：`loadFinished` 即读 DOM 只会拿到骨架，

2. **注入脚本必须 `QString::fromUtf8`**：脚本里的中文字面量（如「作业」）若用 `fromLatin1`
   会逐字节变成乱码，字符串比较永远不匹配——最隐蔽的一个坑。
3. **C++ 原始字符串终止符 `)JS"` 会吃掉脚本结尾的 `)`**：IIFE 结尾要写 `})())JS"`，
   否则脚本变成未调用的函数表达式，`runJavaScript` 静默返回空。
