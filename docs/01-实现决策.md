## 1. moc 与原始字符串字面量（会导致只在链接期暴露的诡异错误）

### 现象

`RepositoryTests.cpp` 编译通过，但链接时报：

```
error LNK2001: unresolved external symbol "RepositoryTests::metaObject(void)const"
error LNK2001: unresolved external symbol "RepositoryTests::qt_metacast(char const *)"
error LNK2001: unresolved external symbol "RepositoryTests::qt_metacall(...)"
```

检查生成物发现 `RepositoryTests.moc` 是 **0 字节**，而其他测试的 `.moc` 都正常。
手工跑 moc 得到提示：`No relevant classes found. No output generated.`

### 根因

moc 不是完整的 C++ 解析器。它会把字符串字面量里的换行**替换成空格**
（因为它需要在字面量内部识别 `#define`），于是字面量之后的代码在 moc 眼里会**错位**；
再叠加 moc 对单个 token 的长度上限，最终 moc 认为文件里没有需要处理的类。

触发条件是「在含 `Q_OBJECT` 的类体内部，使用**跨行**的原始字符串字面量」：

```cpp
class MyTests : public QObject {
    Q_OBJECT
private slots:
    void f() {
        // ❌ 这会破坏 moc：字面量跨行，且总长较长
        const QString json = QStringLiteral(R"JSON({"courses":[
            {"id":90001}
        ]})JSON");
    }
};
```

### 规避方式

**含 `Q_OBJECT` 的文件里不要写跨行的原始字符串字面量。** 三选一：

1. 把长 JSON/脚本放到**不含 `Q_OBJECT`** 的头文件里（如 `tests/support/Fixtures.h`）——
   多行原始字符串放在那里是安全的，因为那个文件不会被 moc 处理。
2. 用「多行普通字面量拼接」代替原始字符串（见 `WebEnginePageBridge.cpp` 的 JS）。
3. 直接构造对象，不经过 JSON 文本（见 `RepositoryTests` 的
   `courses_removedCourseIsSoftDeletedNotErased`）。

> 排查脚本：`v1/_probe/find_moc_breaker.py` 会逐个删除类成员并重跑 moc，
> 定位到底是哪一段代码破坏了 moc 输出。

### 二次踩坑：AUTOMOC 缓存

即使修好了源码，CMake 仍可能因为 `build/.../*.moc` 已存在（0 字节）而**不重新生成**。
修复后必须清掉 `build/` 重新配置，否则会看到「代码改了但错误一样」。

## 2. Qt WebChannel：注入方式决定成败

目标是在站点页面上下文里执行 `fetch`（复用真实浏览器会话），把结果经
QWebChannel 回传给 C++。实测三步才走通：

### 坑 1：`QWebEngineScript` 注入 qwebchannel.js 不生效

```cpp
// ❌ 实测无效：页面自检显示 hasQWebChannel = false
QWebEngineScript script;
script.setSourceCode(qwebchannelSource);
script.setInjectionPoint(QWebEngineScript::DocumentCreation);
script.setWorldId(QWebEngineScript::MainWorld);
page->scripts().insert(script);
```

页面自检输出（`tools/verify_live.cpp` 的 V1b 探针）：

```json
{"hasQt":true,"hasTransport":true,"hasQWebChannel":false,"hasRequestFn":true}
```

注意 `hasQt` 与 `hasTransport` 都是 `true`，说明主世界本身是通的，
**只有被插入的那段源码没有执行**，原因未明。

**可行做法**：在 `loadFinished` 之后用 `runJavaScript` 执行同一份源码，
`hasQWebChannel` 立刻变成 `true`。因此本项目的 `ensurePageScripts()`
走的是 `runJavaScript` 这条路。

### 坑 2：自己实现 WebChannel 线协议行不通

既然 `qwebchannel.js` 不好注入，我曾按协议直接发消息：

```js
qt.webChannelTransport.send(JSON.stringify({type:'QWebChannel', objects:['njulmsBridge']}));
qt.webChannelTransport.send(JSON.stringify({type:'invokeMethod', object:'njulmsBridge',
                                            method:'deliver', args:[text], id:1}));
```

**实测收不到任何回执**：`onmessage` 一次都没被调用（计数器恒为 0），
而 fetch 明明已经成功（未决请求数从 0 变成 1）。
原因是通道只有在客户端完整构造之后才开始投递消息。

**结论**：必须用官方 `qwebchannel.js` 构造 `QWebChannel`，不要手写协议。

### 坑 3：通道构造是异步的

```js
new QWebChannel(transport, function (channel) { /* 这里才拿到 channel */ });
```

因此包装器必须**先等通道就绪再发请求**，否则 `channel.objects` 是空的。
本项目的 `__njulmsAwaitChannel()` 用轮询等待，最多 5 秒。

### 最终可用形态

```
loadFinished
  → runJavaScript(qwebchannel.js 源码)        // 定义 QWebChannel
  → runJavaScript(fetch 包装器)               // 定义 __njulmsRequest
  → 页面内: new QWebChannel(transport, cb)    // 异步就绪
  → 页面内: fetch(path, {credentials:'same-origin'})
  → 页面内: channel.objects.njulmsBridge.deliver(JSON.stringify(result))
  → C++: PageBridgeTransport::deliver → 回调
```

## 3. 内容摘要（contentHash）不能区分 Absent 与 Missing

### 现象

`RepositoryTests::assignments_repeatedSnapshotDoesNotDuplicate` 失败：
同一份数据第二次采集时，本该 `unchanged` 的记录变成了 `updated`。
日志定位到具体记录，是**没有 `publish_time` 字段**的那一条。

### 根因

- Parser 看到响应里**没有** `publish_time` 这个 key → `FieldState::Missing`
- 数据库里该列是 NULL，读回来只能得到 `Observed<QDateTime>::absent()`
- 若 token 把两者编码成不同的字符（`M` 与 `E`），摘要就永远不相等，
  于是每次同步都判定「内容变了」并反复 UPDATE。

### 修法

`valueToken()` 把 `Absent` / `Missing` / `Invalid` 统一编码为 `N`（无值），
只有真正有值时才编码为 `V<长度>:<内容>`。

这样**不会**丢失「字段从有值变成 null」的检测能力（`V...` → `N` 仍然不同），
只是不再区分「确认空」与「没解析到」——这两者的差异属于解析质量问题，
由 `parse_errors` 与 `FieldState` 负责，不应影响内容摘要。

## 5. 日志脱敏：实测踩到的 4 个坑

需求第五节要求日志不得出现密码、Cookie、令牌、验证码与完整认证跳转 URL。
实现 `utils/Redact.cpp` 时踩到：

1. **拼接原始字符串会让正则失效**
   `QStringLiteral(R"((?i)\b(password|...|\b)" R"(sessionid|...)" ...)`
   拼接后模式里混进了 `R"(` 与 `)"` 字面量，`QRegularExpression` 编译失败，
   `replace()` 静默什么都不做 —— 凭据照样落盘。
   **必须用普通字面量拼接正则。**

2. **关键字前不能加 `\b`**
   站点的盐值字段叫 `pwdEncryptSalt`，前面的 `d` 是单词字符，
   `\b` 在 `d` 与 `E` 之间不存在，`encryptsalt` 永远匹配不上。

3. **也不能加否定环视 `(?<![A-Za-z0-9])`**
   同样因为前面是 `d` 而被挡掉。结果是 `pwd` 与 `encryptsalt` 两条备选全部失败。
   代价是 `compass=123` 之类的普通词会被误伤 —— **有意接受**：
   日志多一处 `***` 无害，凭据泄漏有害。

4. **分隔符必须单独捕获**
   若写成 `(keyword)(?=...)\s*(?:[=:])\s*(value)`，分隔符属于非捕获组，
   替换时会被一起丢掉，得到 `service***` 而不是 `service=***`。
   必须 `(keyword)(\s*(?:[=:]|%3[dD])\s*)(value)`，替换用 `\1\2***`。

### 额外发现：Chromium 的 JS 控制台会泄漏完整认证 URL

实测站点把认证跳转 URL 打进控制台，而 Qt WebEngine 会把它作为
`context.category == "js"` 的消息交给消息处理器：

```
js: The Content-Security-Policy directive name 'authserver.nju.edu.cn' ...
    source: https://authserver.nju.edu.cn/authserver/login?service=https%3A%2F%2F...
```

该 URL 的参数是 **URL 编码**的（`service%3D`），只认 `=` 的规则匹配不上。
处理方式有两层：

- `Logger::handleMessage` **直接丢弃** `category == "js"` 的消息 ——
  那是第三方内容，不是本程序的日志，不记录最可靠；
- `Redact` 的关键字规则同时覆盖 `=` 与 `%3D`，作为第二道防线。

### `QUrl::toString()` 会把 `*` 编码成 `%2A`

所以 URL 场景下脱敏先用只含字母的占位符，结构化处理之后再换回 `***`。

## 6. 作业状态是**推导**字段

站点**没有**一个已验证的原始状态字符串字段。`AssignmentStatus` 是由
`submitted` / `is_closed` 与截止时间推导出来的，因此：

- UI 上必须标注为推导值，不能让人误以为是站点权威字段；
- 推导顺序很重要：**只对「未提交」分支判断是否逾期**。
  若把截止时间判断前置，一条「已提交且已截止」的作业会被误判为 Overdue；
- 未提交且截止时间未知时返回 `Missing`，而不是硬猜 `Pending`。

## 7. `homework-activities` 不含 `unique_key`

实测（6/6 条）：

| 接口 | 含 `unique_key` |
| --- | --- |
| `GET /api/courses/{id}/homework-activities` | ❌ 一条都没有 |
| `GET /api/courses/{id}/activities` | ✅ 每条都有 |

因此对作业列表接口而言，「按 `{type}-{id}` 推导」是**常态而不是兜底**。
已实测确认站点规则就是 `unique_key == "{type}-{id}"`（6/6 完全吻合），
所以推导值可靠；但两个接口必须解析出**相同**的 `sourceId`，
否则同一份作业会因为走了不同接口而被写成两条记录（已有测试断言这一点）。

## 8. `page_size` 可调，分页可被压平

实测 `page_size` 取 10 / 50 / 200 都被原样接受并回显。因此本项目
一次请求取全量（`page_size=200`），把「翻页」降级为「单次快照」，
从根本上规避「翻页期间列表变化导致漏项」（需求场景 H）。

仍用响应里的 `total` 做完整性校验：解析条数与 `total` 不一致时
`snapshotComplete = false`，**断点不推进**。

### 若服务端夹取了 page_size，会自动翻页

实现位于 `fetchAssignmentsPage()`。要点：

- 各页结果按 `sourceId` **去重合并**，而不是简单累加：
  翻页期间列表若发生插入/删除，同一条目可能出现在两页里（重复），
  按标识合并可以化解；真正危险的是「前移到已取过的页」导致漏项，
  这由最后的 `total` 校验兜住 —— 数量对不上就不算完整。
- 有 100 页安全上限（`kMaxPages`），避免服务端分页元数据异常时无限请求。
- 合并后与 `total` 不符时**不声称完整**，下次同步会重试整门课。

## 9. 会话失效的判定依据

实测：未登录访问 `/api/my-courses` 返回 **HTTP 401**。

但**不能只依赖状态码**——站点在会话过期时也可能返回登录页 HTML 且状态码为 200。
因此判定条件是**响应体能否解析为 JSON 且含 `courses` 数组**：

- 非 JSON（HTML）→ `SessionExpired`，暂停采集并提示重新登录
- HTTP 401/403 → `SessionExpired`
- 是 JSON 但无 `courses` 键 → `UnexpectedShape`，记录解析错误
- 是 JSON 且 `courses` 为空数组 → **合法状态**，不是错误

## 11. 一个进程只允许一个 QWebEngineProfile 存储路径

### 现象

在一个进程里对**同一个存储路径**创建第二个 `QWebEngineProfile`，
Chromium 会直接中止进程：

```
FATAL: Check failed: !HistoryPathsTracker::GetInstance()
Exception code: 0x80000003   (断点异常)
```

### 触发场景

`MainWindow` 的构造函数里会创建 Profile。于是：

- **打开第二个主窗口 = 进程崩溃**；
- 自动化测试里连续构造多个 `MainWindow` 也会崩。

这个缺陷**不是**靠代码审查发现的——是 `tests/MainWindowSmokeTests.cpp`
的 `survivesRepeatedConstruction` 用例在 `ctest` 下约 1/3 概率崩溃才暴露出来。
UI 层此前完全没有测试覆盖，所以这个崩溃一直潜伏着。

### 修法

把 Profile 提升为**进程级共享对象**（`acquireSharedProfile()`）：

- 用 `QHash<QString, QWebEngineProfile*>` 按清理后的路径缓存；
- 同一个路径返回同一个对象，多个窗口共用一份会话与缓存；
- 缓存持有对象（无父对象、进程级生命周期），页桥改用 `QPointer` 弱引用，
  避免悬垂与误删；
- 顺便省掉了第二个窗口重复初始化 Chromium 的开销（冒烟测试从 37s 降到 13s）。

### 仍然存在的约束

路径**不同**的多个 Profile 依旧会触发同一个 Chromium 断言。
因此本程序在一个进程内只支持一个 Profile 存储路径。
若将来要做「多账号切换」，必须换进程或换 Chromium 的 profile 隔离方式，
不能靠再 new 一个 `QWebEngineProfile`。

## 12. 假信号：重建页面时的 "page destroyed"

`WebEnginePageBridge::initialize()` 会用持久化 Profile 重建页面，
旧页面通过 `delete d->page` 释放。而旧页面上连着：

```cpp
connect(d->page, &QObject::destroyed, this, [this]() {
    d->ready = false;
    emit becameUnavailable(QStringLiteral("page destroyed"));
});
```

于是那次 `delete` 会立刻发出「页桥不可用」——**而页桥马上就会被新页面替换**。
这是纯粹的误报，但会让适配器与上层以为浏览器挂了。

**修法**：删除旧页面之前先 `disconnect(d->page, nullptr, this, nullptr)`，
并在创建新页面后显式把 `d->ready` 置回 false（等待新的 loadFinished）。

同样是由 `MainWindowSmokeTests` 的告警输出发现的
（修复前每次构造都会打印 "page bridge became unavailable"）。
