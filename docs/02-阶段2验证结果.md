## 三、V1：页面内 fetch 与结果回传（通过）

这是整个架构的关键前提。结论：**可行**，但正确的接线方式不明显，
过程中排除了两个错误方案（详见 `01-实现决策.md` 第 2 节）。

### 最终可用链路

```
QWebEnginePage::loadFinished
  → runJavaScript(:/qtwebchannel/qwebchannel.js 源码)   // 定义 QWebChannel
  → runJavaScript(fetch 包装器)                        // 定义 __njulmsRequest
  → 页面内 new QWebChannel(qt.webChannelTransport, cb) // 异步建立通道
  → 页面内 fetch(path, {credentials:'same-origin'})    // 复用真实会话
  → 页面内 channel.objects.njulmsBridge.deliver(...)   // 回传
  → C++ PageBridgeTransport::deliver → 适配器回调
```

### 实测证据

页面自检输出（`tools/verify_live.cpp` 的 V1b）：

```
page globals: {"hasQt":true,"hasTransport":true,"hasQWebChannel":true,
               "hasRequestFn":true}
```

请求发出后确实收到了 C++ 回调（适配器给出了明确的错误分类，而不是超时）：

```
authenticated : false
error code    : 1        // ErrorCode::SessionExpired
error message : server rejected the session
```

### 被排除的两个错误方案（都已实测失败）

| 方案 | 现象 |
| --- | --- |
| `QWebEngineScript`（DocumentCreation + MainWorld）注入 qwebchannel.js | 页面里 `hasQWebChannel = false`，注入的源码根本没执行 |
| 自己按线协议实现 WebChannel 客户端 | `onmessage` 一次都没触发（计数器恒为 0），fetch 成功但结果永远回不来 |

> 由此产生的实现约束：**必须用官方 qwebchannel.js，且用 `runJavaScript` 注入。**

## 四、V2：会话失效的真实形态（已实测）

### 实测结果

未登录状态下请求 `POST /api/my-courses`：

```
error code    : 1  (SessionExpired)
error message : server rejected the session
```

对应 **HTTP 401**。适配器按 `httpStatus == 401 || 403` 判定为 `SessionExpired`，
并发出 `sessionExpired` 信号。

### 关键验证点

**没有**把失效会话解析成「0 门课程的合法列表」：

```
authenticated : false     ← 不是 true
course count  : 0         ← 但 authenticated 已经是 false
```

这正是需求场景 C 要求的区分。`ResumeTests` 覆盖了四种情况：

| 响应形态 | 期望判定 | 测试用例 |
| --- | --- | --- |
| 登录页 HTML + 状态码 200 | `SessionExpired`（不看状态码） | `scenarioC_expiredSessionIsNotAnEmptyList` |
| HTTP 401 | `SessionExpired` | `scenarioC_http401IsTreatedAsLoginRequired` |
| JSON 但没有 `courses` 键 | `UnexpectedShape` | `courses_missingKeyIsReportedNotTreatedAsEmpty` |
| JSON 且 `courses` 为空数组 | **成功**（合法空课程表） | `scenarioC_genuinelyEmptyCourseListIsNotAnError` |

### 顺带发现的一个真实泄漏

站点会把完整的认证跳转 URL 打印到 JS 控制台，Qt WebEngine 把它作为
`category == "js"` 的消息交给日志处理器，导致
`https://authserver.nju.edu.cn/authserver/login?service=https%3A%2F%2F...`
**原样进入日志文件**（参数是 URL 编码的，只认 `=` 的旧规则匹配不上）。

已修：日志处理器直接丢弃 `js` 类别的第三方控制台消息，
同时脱敏规则覆盖 `%3D` 形式。修复后重跑，日志文件中不再出现认证 URL。
这条已加单元测试（`RedactTests::redactsUrlEncodedSeparators`）。

## 五、V3：page_size（部分验证）

上一轮 Python 原型实测 `page_size` 取 10 / 50 / 200 均被服务端原样接受并回显，
`total` 与实际条数一致。本项目据此一次请求取全量，把分页压平成单次快照。

**尚未验证**：`page_size` 的上限（500 / 1000 是否被夹取）。
由于当前无有效会话，本轮未能复测。

**当前代码已实现真正的翻页**（本轮补上，原先只是保守拒绝）：

- 返回条数少于 `total` 时自动继续取下一页；
- 各页结果按 `sourceId` **去重合并**（防翻页期间列表变化导致重复或前移）；
- 合并后数量与 `total` 一致才算完整，否则 `snapshotComplete = false`，断点不推进；
- 有 100 页安全上限，避免服务端分页元数据异常时无限请求。

`PaginationTests`（8 个用例）覆盖：单页完整、多页跟随与合并（25 条 / 3 页）、
重复页去重、安全上限、无 `total` 时拒绝声称完整、第二页会话失效。

## 五之二、离线字段契约审计（本轮新增，不需要有效会话）

由于会话过期，本轮无法跑真机，于是把解析器的**全部字段假设**与既有 13 份真实
抓包（12 条作业）做了穷举交叉核对，而不是只依赖此前抽样看过的几条。

审计脚本：`_probe/audit_field_assumptions.py`、`_probe/audit_unmodelled_fields.py`。

### 结论：解析器假设与每一个真实条目都一致

| 字段 | 真实出现情况 | 解析器处理 |
| --- | --- | --- |
| `id` / `title` / `deadline` / `end_time` / `updated_at` / `type` | 12/12 存在 | Present |
| `data.description` | 12/12 存在 | Present |
| `data.publish_time` | **8/12 存在，4/12 整个 key 缺失** | Present / **Missing** |
| `score` | **缺失 8/12、null 2/12、有值 2/12** | **Missing / Absent / Present 三种都真实出现** |
| `submitted` | 6/12 存在，6/12 缺失（仅 `/activities` 有） | Present / Missing，缺失时回落 `is_closed` |
| `is_closed` | 12/12 存在 | 回落路径可用 |
| `is_started` | 6/12 存在 | 未依赖 |
| `unique_key` | **6/12 存在（全部来自 `/activities`）** | 存在则直接用，缺失则按 `{type}-{id}` 推导 |
| `unique_key == "{type}-{id}"` | **6/6 完全吻合，0 处不符** | 推导规则得到实锤支持 |

三个直接把设计"证伪或证实"的点：

1. **`publish_time` 确实有 4/12 完全缺失** —— 所以"发布时间必须可空、绝不能用采集时间
   兜底"不是过度设计，而是必需。
2. **`score` 的三种状态在真实数据里都出现过**（缺失 / null / 有值）。
   这正好说明为什么必须区分 `Missing` 与 `Absent`：若把"缺失"写成 NULL，
   就会把"这次接口没给"误当成"确认没有成绩"。
3. **`unique_key` 只存在于 `/activities`**，且 6/6 等于 `{type}-{id}`。
   两个接口必须解析出相同的 `sourceId`，否则同一份作业会被写成两条记录。

### 未建模字段的显式清单

审计同时列出了真实响应中存在、但 `Assignment` 模型**没有**保存的字段
（顶层 70 个、`data` 下 22 个）。这是有意为之，不是遗漏：

- 需求文档第三节第 3 点给出的 `Assignment` 模型字段是封闭集合，其中**不含**
  `created_at`、`start_time`、`sort` 等；
- 需求第四节点名要求的 `submitted` 与 `score` **已建模**；
- 其余字段（rubric、inter/intra review、knowledge node、group set 等）
  与"作业采集与提醒"这一目标无关。

需要强调的是：**没有**任何需求要求捕获的字段处于未建模状态。
审计脚本可随时重跑，用于确认这一点仍然成立。

> 顺带说明：`sort` 字段（12/12 存在）是站点自己的稳定排序键。本项目不使用它作为
> 同步断点——需求明确禁止用排序位置推断进度——但若将来需要确定性排序，它是可用依据。

### 9.9 接口探索：跨课程待办 `/api/todos`（v2 快速增量的依据）

通过"从页面已加载的 120 个 JS bundle 里静态提取 `/api/...` 路径"的方式（只读扫描
前 60 个 bundle、约 8 MB，得到 264 条候选路径），再对候选做只读 GET，确认了：

```
/api/todos -> 200，keys=todo_list
  items=1；item keys: course_code,course_id,course_name,course_type,end_time,id,
                     is_locked,is_student,prerequisites,title,type
  end_time raw: 2026-10-15T15:59:00Z  parsedOk: true
  distinct types: homework
其余候选（/api/todo-list、/api/todo_list、/api/upcoming、/api/calendar/activities）-> 404
/api/activities?type=homework -> 500（站点自身故障）
```

结论：`/api/todos` 是真实的跨课程聚合接口，但只覆盖"待办/未完成"条目，
因此只能作为**变更信号**（配合按需深扫与周期性全量对账），不能替代完整快照。
实现与取舍见 `03-v2变更记录.md` 第 6 节。
