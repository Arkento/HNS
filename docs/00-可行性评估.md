## 1. 结论

**技术可行，可以开工。** 三条硬事实决定了架构，任何实现都必须遵守：

1. **登录必须由人工完成**：统一身份认证在密码登录时强制滑块验证，与是否自动化无关；绕过验证码既不合法也不可靠 → 采用「持久化浏览器 Profile + 人工登录一次 + 每日保活」的半自动策略。
2. **数据必须走「已登录页面内的同源 fetch」**：站点是 SPA 且会检测 DevTools 并清空页面渲染，DOM 解析路线不可靠；而站点自身的 JSON 接口稳定可用（已实测）。
3. **没有可靠的增量游标**：站点未提供"给我更新过的数据"这类接口，且 `/activities` 连分页元数据都没有 → 增量同步必须退化为「全量重扫 + 稳定唯一键去重 + 内容摘要判变」。

本重建版（v2）将上一版记录的全部已知缺陷（13 项实现缺陷 + 2 项架构约束）在设计与代码层面修掉，并新增单实例保护与会话策略文档化，详见第 6 节。

**需要人工配合的唯一事项**：真机端到端复测需要人工登录一次（见第 8 节）。

## 2. 项目范围摘要

- 只采集当前用户正常登录后**有权限访问**的课程与作业。
- 目标数据：课程任务、作业标题/说明/详情链接、发布时间（如存在）、截止时间、状态等页面明确提供的字段。
- 功能：人工登录、全量采集、增量同步、SQLite 持久化、断点续传与异常恢复、定时同步、运行日志与错误查看、去重与变更更新。
- 技术栈：C++17、CMake、Qt 6（Widgets + WebEngine + WebChannel）、SQLite（Qt SQL）。
- 网站专属逻辑（URL、字段名）与数据库/调度/同步机制解耦；站点改版只需改适配器与解析器。

## 4. 站点登录策略（决定架构，均已实测）

### 4.1 三段式认证链

```
lms.nju.edu.cn ──302──► lms-identity.nju.edu.cn（Keycloak，realm=nju，CAS 协议）
                ──302──► authserver.nju.edu.cn（南大统一身份认证）
                ──认证完成──► CAS 回跳 → Keycloak SSO → 回到 LMS 下发应用会话
```

### 4.2 登录方式与强制滑块

- 支持：扫码、账号密码、短信动态码、FIDO。
- **密码登录强制滑块验证**：`captchaSwitch = 2`；`GET /authserver/checkNeedCaptcha.htl` 返回 `{"isNeed": true}`；失败计数为 0 时也触发 → 是站点策略，不是失败惩罚。
- 结论：不做任何验证码识别/绕过；`relogin` 场景由人工完成滑块或扫码。密码加密由页面自身完成，无需在程序中复现加密算法。

### 4.3 会话与 Cookie 生命周期

| Cookie | 域 | 类型 | 实测有效期 |
| --- | --- | --- | --- |
| `session` | lms.nju.edu.cn | 持久 | **约 24 小时，每次访问顺延** |
| `role_token` | lms.nju.edu.cn | 持久 | 同 `session` |
| `KEYCLOAK_IDENTITY` | lms-identity.nju.edu.cn | 会话级 | 浏览器关闭即失 |
| `KEYCLOAK_SESSION` | lms-identity.nju.edu.cn | 持久 | 约 1 年 |
| `CASTGC` | authserver.nju.edu.cn | 会话级 | 浏览器关闭即失 |
| `MULTIFACTOR_BROWSER_FINGERPRINT` | authserver.nju.edu.cn | 持久 | 约 1 年 |

由此得出两条设计约束：

1. LMS `session` 是滚动过期的 → **只要每天至少访问一次，登录态可无限顺延**（程序内置保活：每次同步/状态检查都算一次访问）。
2. Keycloak/CAS 会话级 Cookie 在本项目里**不会**随进程关闭丢失：Qt 的 `ForcePersistentCookies`
   会把它们写入磁盘并在下次启动时恢复。2026-10-09 实测（Profile 副本、删除全部
   `lms.nju.edu.cn` 会话 Cookie 以模拟过期）：重启后站点经 CAS/Keycloak 静默换回新会话，
   接口判定 `authenticated = true`（13 门课程），**无需人工登录**。
   设计约束因此修正为：**不主动延长任何 Cookie 的生命周期**（使用默认行为即可），
   并且不再假设"每次重启都要人工登录"；只有学校侧 SSO 会话本身失效时才需要人工认证，
   届时由界面明确提示。

### 4.4 本地实测的其它要点

| 项 | 实测结论 |
| --- | --- |
| 登录页 DOM 陷阱 | 同一页面存在多套登录表单，`input#username` 出现 3–4 次（多为隐藏）→ 定位必须用"可见元素"，程序内注入脚本同理 |
| 反 DevTools | LMS 应用侧检测 DevTools（控制台报 `You don't have permission to use DEVTOOL!`）并清空部分渲染；**认证页与 JSON 接口不受影响** |
| 登录判定 | **不能**以"首页加载成功"判定；必须验证受保护接口返回可解析 JSON（含 `courses` 数组） |
| 会话失效形态 | 实测 HTTP 401；同时按需求场景 C 处理"200 + 登录页 HTML"的情形，两种都判为需登录，绝不解析成空列表 |

## 5. 数据获取可行性（实测证据）

### 5.1 已实测的接口契约

| 接口 | 方法 | 实测结果 |
| --- | --- | --- |
| `/api/my-courses` | POST，body `{}` | 200，约 11 KB，返回 13 门课程；无需 CSRF token；课程含 `url` |
| `/api/courses/{id}/homework-activities?page=1&page_size=…` | GET | 200，约 14.5 KB；`page_size` 实测 10/50/200 被原样接受；返回 `total` |
| `/api/courses/{id}/activities` | GET | 200，约 16 KB；**不返回分页元数据**，无法证明集合完整 → 不作为断点依据 |

### 5.2 字段契约（对 13 份真实抓包的穷举审计）

| 字段 | 真实情况 | 设计要求 |
| --- | --- | --- |
| `id` / `title` / `deadline` / `end_time` / `updated_at` / `type` | 12/12 存在 | 必须映射 |
| `data.description` | 12/12 存在（HTML 字符串） | 保存原文，UI 渲染时处理 |
| `data.publish_time` | **8/12 存在，4/12 整键缺失** | 可空；缺失时**保留库中原值**，绝不用采集时间兜底 |
| `score` | 缺失 8/12、null 2/12、有值 2/12 | 必须区分「缺失 / 明确为空 / 有值」三态 |
| `unique_key` | 仅 `/activities` 有；实测 6/6 等于 `{type}-{id}` | 有则直接用；无则按实测规则推导，保证两接口结果一致 |
| `submitted` / `is_closed` | `submitted` 仅 `/homework-activities` 有 | 状态字段按"有则用、无则按实测规则回退"处理 |
| 所有时间戳 | ISO 8601 UTC（`Z`） | 统一转 UTC 存储，展示转 UTC+8 |

### 5.3 已打通的取数链路（关键前提）

```
QWebEnginePage::loadFinished
  → runJavaScript(:/qtwebchannel/qwebchannel.js 源码)   // 官方脚本，必须 runJavaScript 注入
  → runJavaScript(fetch 包装器 + 建立 QWebChannel 通道)
  → 页面内 fetch(path, {credentials:'same-origin'})      // 复用真实会话
  → channel.objects.<bridge>.deliver(...)                // 回传 C++
  → C++ 侧 QJsonDocument 解析
```

实测排除的两个错误方案（**不要再尝试**）：

| 方案 | 现象（实测） |
| --- | --- |
| 用 `QWebEngineScript` 注入 qwebchannel.js | 页面内 `hasQWebChannel = false`，注入源码不执行 |
| 自行按线协议实现 WebChannel 客户端 | `onmessage` 从不触发，结果永远回不来 |

### 5.4 分页与完整性

- 首选 `page_size=200` 把分页压平成"单次快照"，并以响应里的 `total` 校验。
- 若服务端夹取 `page_size`：自动翻页，逐页按 `sourceId` 去重合并，合并数 == `total` 才算完整；否则 `snapshotComplete = false`，**不推进断点**。
- 安全上限 100 页，防止服务端元数据异常导致无限请求。

### 5.5 性能实测（决定频率策略）

| 指标 | 实测值 |
| --- | --- |
| 最小全量同步成本 | **14 次请求 ≈ 200 KB，约 5–15 秒** |
| 接口延迟 | 76 ms – 2.7 s（首次较慢，其后 175–263 ms） |
| 请求策略 | 串行 + 相邻请求间隔 400 ms + 课程间 300 ms；失败重试 ≤3 次、退避递增 |

## 7. 安全、隐私与合规

| 主题 | 措施 |
| --- | --- |
| 认证 | 只允许人工完成统一身份认证；不识别/不绕过验证码、多因素；不伪造身份 |
| 凭证存储 | 不保存密码；浏览器 Profile（内含会话 Cookie，等同于凭证）可配置路径、不入 Git、不写日志、建议 NTFS 权限收紧 |
| 日志 | 白名单字段（任务、批次、计数、错误类型、时间）；全量过脱敏；丢弃第三方 JS 控制台消息；日志大小轮转 |
| 请求频率 | 串行 + 固定间隔；默认定时周期 60 分钟；连续失败熔断；不在未确认规则前提高频率 |
| 数据范围 | 只访问当前用户有权访问的课程；退出权限的课程软删除保留（不物理删除） |
| 反对抗 | 不伪装 UA、不注入对抗脚本；若遇 WAF/风控拦截，暂停并提示用户，不做对抗性调整 |
| 依赖许可 | Qt 6 采用 LGPLv3（非商业）→ 动态链接、随包提供许可证与可替换性说明；部署包含 `QtWebEngineProcess` |

## 9. v2 目标架构与目录

```
Qt WebEngine 浏览器与登录（BrowserSession）
        ↓ IPageBridge（抽象：在已登录页面里发一次同源请求）
认证状态管理（AuthManager：Unknown / Authenticated / NeedLogin）
        ↓
NjuLmsAdapter 网站适配器（接口路径、分页、去重、完整性判断）
        ↓
AssignmentParser 解析与标准化（三态字段、UTC 时间、内容摘要、稳定 sourceId）
        ↓
SqliteRepository（唯一 SQL 入口：UPSERT、事务、软删除、运行记录、断点）
        ↕
SyncManager（全量/增量、批次与断点、暂停/继续/取消、恢复）
        ↑
Scheduler（QTimer 定时、单飞、启动孤儿状态回收）
UI：MainWindow（只显示与转发；登录、按钮、进度、列表、日志）
```

目录（与开发指令第六节一致）：

```
src/
  app/ browser/ auth/ adapters/ parser/ models/ repository/ sync/ scheduler/ ui/ utils/
tests/
data/  logs/   （运行时创建，可用环境变量覆盖）
docs/          （本文件与后续验证报告）
```

关键设计：

- **断点粒度 = 一门课程的完整作业快照**：作业写入 + 批次记录 + 断点更新处于同一个 SQLite 事务；只有"能证明完整"的快照才推进断点。
- **恢复策略 = 重新扫描全部课程**：整份快照写入是幂等的，重扫天然避免漏判；不依赖任何时间戳推断进度。
- **消失检测 = 软删除**：快照中消失的作业标记为不在场，保留历史。
- **推导字段显式标注**：作业"状态"与"详情链接"为推导值（站点无现成字段），在模型与 UI 中注明来源。

## 10. 实施计划与验收标准（按开发指令阶段 1–6）

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| 1 | 工程骨架、主窗口、打开站点、人工登录、登录状态 | 程序可编译运行；能打开站点并正确判定登录态 |
| 2 | 真实页面/接口验证、解析器 | 解析结果与页面一致；未验证字段不伪造；脱敏样本入库为测试数据 |
| 3 | SQLite 与 Repository | 重复导入不产生重复记录；解析失败不覆盖有效值 |
| 4 | 全量采集与断点续传 | 批次中途强制退出后可恢复，不漏不完 |
| 5 | 增量同步 | 作业变化更新原记录；不产生重复 |
| 6 | 调度与 UI 完善 | 重启识别未完成任务；登录失效安全暂停；日志脱敏 |

## 11. 结论

技术路线、工具链、站点契约三者都已实测验证，v2 可以按阶段开工。真正的风险不在技术，而在两条边界上：

1. **会话的人工性**——滑块验证是学校策略，方案是人工登录一次 + 每日保活 + 失效时明确提示；
2. **访问频率的合规性**——站点无公开规则，方案是保守频率（分钟级不可行、小时级起步）并保留用户确认开关。

除此之外，本报告第 6 节的缺陷清单已在 v2 的设计与实现中逐条修掉。
